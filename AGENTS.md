# AGENTS.md

Этот файл нужен как постоянная подсказка для дальнейшей работы над проектом `OBS Auto Capture Plugin`.

## Цель проекта

Сделать нативный Windows-плагин для OBS Studio, который добавляется как источник и автоматически захватывает активное окно из заранее выбранного списка приложений.

## Основные требования

- Плагин должен быть написан на `C++17`
- Плагин должен собираться через `CMake`
- Базовая интеграция идет через `libobs` и OBS Plugin API
- Основная платформа на старте: `Windows`
- В логике нужно использовать `Win32 API` для поиска окон и процессов

## Ожидаемое поведение источника

- Пользователь добавляет источник в OBS
- В свойствах источника указывает список `.exe`, которые нужно отслеживать
- Плагин автоматически обнаруживает появление этих процессов
- Плагин определяет, какое из подходящих окон сейчас активно на экране
- Если возможно, источник должен уметь работать как:
  - аналог `Window Capture`
  - аналог `Game Capture`
- В идеале плагин сам выбирает лучший режим захвата

## Архитектурный ориентир

- Не делать внешний костыльный лаунчер
- Делать именно OBS plugin module
- Основной source id: `auto_app_capture_source`
- Внутри держать отдельный runtime-state для:
  - списка целевых процессов
  - текущего активного окна
  - текущего PID
  - текущего заголовка окна
  - выбранного режима захвата
- Желательно предусмотреть внутренний дочерний source для реального захвата позже

## Правила работы с Qt

- Qt живёт только в `settings-window.cpp`. Заголовок `settings-window.hpp` намеренно без Qt: источник крутится в графическом потоке, и Qt-заголовков он видеть не должен.
- Qt трогать можно только из UI-потока. Окно открывается исключительно из колбэка свойства — они и так выполняются в UI-потоке. Из `Update`, `Tick` или рендера обращаться к окну нельзя ни при каких условиях.
- Окно правит **копию** настроек и отдаёт её источнику по ОК или «Применить». Источник может быть в эфире, недоделанная правка попасть в него не должна.
- Источник могут удалить из сцены при открытом окне. libobs обычному `QDialog` об этом не сообщает, поэтому окно держит слабую ссылку и проверяет её по таймеру.
- Всё под `AUTO_CAPTURE_HAS_UI`, который ставится только если доступны и Qt, и frontend API. Без них плагин обязан собираться и оставаться настраиваемым через свойства источника.
- Цвета не хардкодить: у пользователя может стоять светлая тема или своя `.ovt`. Отличие от вида OBS достигается компоновкой, а не своей палитрой.
- Qt-библиотеки рядом с плагином не класть — OBS поставляет свои, и вторая копия сломает загрузку.

## Правила по совместимости версий OBS

- Собирать только против нижней поддерживаемой версии, сейчас это OBS 30.0.0 в `buildspec.json`. libobs отклоняет модуль лишь тогда, когда он собран против **более новой** версии, поэтому один бинарник работает на всех релизах выше опорного.
- Не поднимать опорную версию ради удобства: это отрежет пользователей. Поднимать только если новый API действительно нужен.
- Новые функции libobs проверять по нижней версии, а не по той, что установлена локально. Символ, которого нет в опорной версии, не даст модулю загрузиться — сборка против опорной версии это и ловит.
- Ниже 30.0.0 шаблон не работает: он конфигурирует OBS ключом `-DOBS_CMAKE_VERSION=3.0.0`, а в 29.1.3 новая система сборки только появилась.
- Диапазон проверен запуском на портативных 30.2.3 и 31.1.2 и на установленной 32.1.2. Проверять надо не загрузку модуля, а создание источника: загрузка доказывает только то, что разрешились символы.
- В тестовой портативной конфигурации `[Basic]` надо писать и в `global.ini`, и в `user.ini`: в OBS 30.2 пользовательские настройки выделили в `user.ini`, и 31 читает только его. Иначе OBS молча создаёт пустую коллекцию сцен, и проверка выглядит как отказ плагина.
- В `cmake/` лежит вендоренная копия шаблона с двумя правками, помеченными `Local change to the vendored template`. При обновлении шаблона их надо перенести.

## Правила работы с потоками

Это самое опасное место проекта, здесь уже было падение OBS:

- libobs откладывает `update` видеоисточника в графический поток. Поэтому `AutoCaptureSource::Update` только читает `obs_data`.
- Любая запись в настройки источника выполняется исключительно в колбэках свойств (UI-поток): `GetProperties`, кнопки и `modified`-колбэки.
- Общего мьютекса на состояние источника в коде нет, хотя раньше документация это утверждала. Всё держится на том, что `Update`, `Tick` и рендер идут в графическом потоке, а колбэки свойств — в UI-потоке и трогают только `obs_data`.
- Единственный фоновый поток — `AddressBarLocator`. Он не вызывает libobs (кроме `blog`) и не трогает состояние источника: обмен идёт только целевым окном и найденным прямоугольником под собственным мьютексом. Останавливается первым в деструкторе источника.

## Правила работы с панелью свойств

- Диалог свойств пересобирает виджеты из уже существующего объекта `obs_properties_t` и не запрашивает у источника новый. Поэтому все свойства создаются один раз в `GetProperties`, а колбэки меняют только видимость, доступность и содержимое списков.
- `obs_source_update_properties()` из колбэка свойства вызывать нельзя: диалог уничтожит виджет, чей обработчик сейчас выполняется.
- Колбэк, вернувший `true`, вызывает пересборку виджетов. На текстовые поля его вешать нельзя — поле пересоздастся прямо во время ввода.
- Настоящих вкладок в API свойств нет: группа всегда рисуется как обычная рамка. Разделы сделаны списком `ui_section` плюс `obs_property_set_visible` на группах.

## Правила работы с графикой

- Свой эффект грузится лениво из `video_render`, то есть уже внутри графического контекста. Повторная попытка после неудачи не делается, иначе ошибка компиляции пишется в лог каждый кадр.
- Освобождение `gs_effect_t` и `gs_texrender_t` идёт через `obs_enter_graphics()`: деструктор источника может быть вызван не из графического потока.
- `gs_texrender_begin` сам сбрасывает матрицу, поэтому зеркалирование снаружи не протекает в дочерний источник и применяется к готовому кадру.
- Набор техник собственного эффекта повторяет `Draw` / `DrawMultiply` / `DrawTonemap` / `DrawMultiplyTonemap` из `default.effect`. Без них включение блюра ломало бы цвет в HDR.
- Любой отказ в пути блюра возвращает `false` и приводит к обычному рендеру: кадр не должен пропадать из-за эффекта.
- `#include` в `.effect` ищет файл только рядом с самим файлом, общий `color.effect` из libobs подключить нельзя. Нужные функции скопированы в шейдер.
- Массивов в uniform-ах парсер эффектов OBS не понимает: зоны передаются как `zone0`..`zone3` плюс `zone_count`.

## Правила работы с UI Automation

Это второе опасное место проекта после потоков, и оно опасно не падениями, а нагрузкой на браузер.

- Обход только по уровням через `FindAllBuildCache` с кэш-запросом на тип и прямоугольник: один вызов через границу процесса на уровень вместо одного на свойство.
- Вниз идти только по элементам верхней пятой части окна и никогда не заходить внутрь узла `UIA_DocumentControlTypeId`. `FindFirst(TreeScope_Descendants, ...)` использовать нельзя: он уходит в страницу, браузер строит дерево доступности всего документа. Измерено на вкладке Twitch: 324 мс и найденный элемент внутри страницы вместо адресной строки. После отсечения — 153 мс и верный элемент.
- Опознавать адресную строку по типу и геометрии, а не по названию: название зависит от языка интерфейса браузера. Chrome и Edge отдают `Edit`, Firefox — `ComboBox` с `Text` внутри.
- Найденный элемент кэшировать и дальше читать только `get_CurrentBoundingRectangle`. Повторный поиск — только когда чтение перестало давать правдоподобный прямоугольник.
- Тайм-ауты обязательны: `CUIAutomation8` → `IUIAutomation2::put_ConnectionTimeout` и `put_TransactionTimeout`. Иначе зависший браузер держит поток.
- `WIN32_LEAN_AND_MEAN` оставляет `interface` неопределённым, поэтому `objbase.h` подключается до заголовков UI Automation.
- Для диагностики удобно собрать локатор в отдельный exe и прогнать по живому окну: так найдены обе ошибки этого этапа.
